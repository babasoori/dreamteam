Run instructions and verification

One clear boundary

Dreamteam

Roster, play scope, assignment ledger, explicit progress reports, and the Courtside status board. Coach and players use session-local MCP tools.

Rex

Native tabs, terminal rendering, input, process hosting, and session persistence. Dreamteam calls the installed CLI with explicit server, session, and block identities.

Codex

The actual conversations, tools, sandbox, and approval dialogs. The human opens each native Rex tab to interact directly.

The Courtside flow

  1. Open Courtside inside Rex. It selects Coach and observes saved state without launching agents.
  2. Press Enter to start Coach and select its native Rex tab. Define the work there, or use N in Courtside to save a play.
  3. Coach dispatches a bounded assignment through Dreamteam tools. The player gets its own background Rex tab.
  4. Return to Courtside using Rex’s tabs. Select a player with 1–6; Enter or O selects its existing native tab.
  5. Review explicit reports and output. An idle process or submitted prompt does not establish completion or acceptance.
  6. X confirms stopping one player. Q offers Stop team and quit, Keep sessions running, or Cancel.

State and ownership

  • dreamteam.toml defines the roster.
  • .dreamteam/possessions/001/state.json beside the roster stores the saved play and project target.
  • .dreamteam/coordination/ in the target project stores assignments and reports.
  • .dreamteam/rex-runtime.json in the target project records Rex server instance, session, block, process and launch identity.

The first Start binds to the current local Rex session. Reopening Courtside reuses those bindings. A different target project has separate bindings. Legacy Herdr runtime files and running sessions are left untouched.

Delivery and cleanup

Starting persists an intent before creating a tab. A lost creation response is reconciled using its unique label; ambiguous launches never produce an automatic duplicate. Input requires a verified idle Codex process and bracketed-paste support. Rex’s acknowledgment means bytes were queued, not that the agent consumed or completed the assignment. Uncertain delivery is not replayed.

Cleanup stops Coach first, closes only verified managed blocks, and leaves the shared Rex server, session, and unrelated tabs alone. A changed server instance or process blocks automatic reuse and cleanup until inspected.

Deliberately small

No embedded terminal emulator, viewer subprocesses, dedicated terminal server, model SDK, or generic backend framework. Courtside remains a Textual status board with forms and read-only previews.

Confirmed passes, explicit acceptance controls, multiple saved plays, automatic restart recovery, and additional agent runtimes remain future work.

Verified boundary

Offline tests cover the play workflow, MCP protocol, assignment ledger, native-tab UI, and Rex lifecycle contracts. A real Rex terminal fixture verified startup, reuse, multiline UTF-8 delivery, output capture, and scoped cleanup. A full real Codex Coach/player roundtrip and native approval interaction on Rex have not yet been verified.
